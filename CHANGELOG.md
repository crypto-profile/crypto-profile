# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor version may change the API. The three crates share one version and are released together.

## [Unreleased]

### Added

- HMAC under a profile (#31), the first family governed outside TLS (decision 0008):
  - `MacAlgorithm` (HMAC-SHA256, HMAC-SHA384, HMAC-SHA512), with `hash()` and `tag_len()`;
  - capability cells: `Approved` on the 3.x line (Table 5 of each certificate's security policy), `AlgorithmTested` on A7855 on the 4.x dynamic build, `Unverified` on the 4.x static build;
  - `admit(profile, options)`, which never refuses, and `Admitted`, both independent of `resolve`; `Admitted` is read-only (`profile()`, `options()`, `macs()`, `excluded()`) and built only by `admit`; `Admitted::admit_mac`, which refuses a MAC the module line lacks with `CryptoError::Unavailable`; `assert_admitted_approved(&admitted, families)`, separate from `assert_module_approves`, which checks the families outside TLS the caller names (Mac, then Kdf, then KeyAgreement), refuses a TLS family with `CryptoError::FamilyNotAdmitted`, and approves nothing for an empty list; in the core crate, `select_admitted` and `AdmittedSelection`;
  - `hmac::Key` and `hmac::Tag`: `Key::new` refuses a MAC the profile does not admit and a key outside `mac_key_floor_bits(profile)` (112 bits, 128 under `bsi`) to `MAC_KEY_MAX_BITS` (524288); `Key::verify` is constant time and takes full-length tags only;
  - `CryptoError::NotInProfile`, for any algorithm outside TLS a profile does not admit, `CryptoError::MacKeyLength` and `CryptoError::MacVerify`;
  - Wycheproof HMAC-SHA256, HMAC-SHA384 and HMAC-SHA512 in the conformance suite.
- HKDF under a profile (#32), the second family governed outside TLS (decision 0010):
  - `KdfAlgorithm` (HKDF-SHA256, HKDF-SHA384, HKDF-SHA512), with `hash()` and `max_output_len()`;
  - capability cells: `Approved` on the 3.x line (Table 5 of each certificate's security policy), `AlgorithmTested` on A7855 on the 4.x dynamic build, `Unverified` on the 4.x static build;
  - `Admitted::kdfs()` and `Admitted::admit_kdf`; `assert_admitted_approved` walks the KDF cells when `Family::Kdf` is named, and first refuses a profile that admits KDFs and an empty `info` (`unrestricted`) with `CryptoError::KdfInfoMayBeEmpty`; in the core crate, `AdmittedSelection::kdfs` and `kdf_info_may_be_empty`;
  - `kdf::derive` with `kdf::Spec::Hkdf`, and `kdf::DerivedKey`: RFC 5869 extract-then-expand in one call, with no public extract; an absent or empty salt is HashLen zeros; an empty `info` is refused under every profile but `unrestricted`; output 1 to 255 × HashLen bytes; an empty secret is refused; the derived key is zeroized on drop;
  - `CryptoError::KdfOutputLength`, `CryptoError::KdfSecretEmpty`, `CryptoError::KdfInfoEmpty` and `CryptoError::KdfInfoMayBeEmpty`, whose `Display` names the KDF generically ("a KDF output of …", "the KDF secret is empty", "an empty KDF info");
  - RFC 5869 Appendix A cases 1-3 and Wycheproof HKDF-SHA256, HKDF-SHA384 and HKDF-SHA512 in the conformance suite.
- The 0.10.0 API shape (#33, decision 0012):
  - `KeyAgreementAlgorithm` (ECDH on P-256, P-384 and P-521, and X25519), with `ALL`, `as_str`, `Display` and `FromStr`, and `Algorithm::KeyAgreement`; `KdfAlgorithm::OneStepSha256`, `OneStepSha384` and `OneStepSha512` (SP 800-56C Rev. 2 §4.1), whose `max_output_len()` is 2^30 bytes;
  - `kdf::Spec`, `#[non_exhaustive]`, with `Spec::Hkdf`; a `Spec` whose algorithm does not match its variant is refused with `CryptoError::KdfSpecMismatch`, before admission;
  - `Family::Mac`, `Family::Kdf` and `Family::KeyAgreement`;
  - `CryptoError::KdfSpecMismatch`, `CryptoError::KeyAgreementPeerKey`, `CryptoError::KeyAgreementPrivateKey` and `CryptoError::FamilyNotAdmitted`.
- ECDH and the one-step KDF under a profile (#33, decision 0011):
  - `ecdh::EphemeralKey` (`generate`, `algorithm`, `public_key`, and `agree`, which consumes the key) and `ecdh::StaticKey` (`from_pkcs8_der`, `from_scalar`, `algorithm`, `public_key`, `agree`): one-pass Diffie-Hellman in both roles on P-256, P-384, P-521 and X25519, each agreement completing into `kdf` in the same call, so the shared secret never leaves the crate. A peer key must be an uncompressed point (or 32 bytes for X25519); compressed and hybrid points and SubjectPublicKeyInfos are refused with `CryptoError::KeyAgreementPeerKey` before the module sees them, and the module validates the rest. A static key is imported only, from PKCS#8 or a raw private key of exactly the field length; `CryptoError::KeyAgreementPrivateKey` refuses anything else;
  - `kdf::Spec::Dhkem { algorithm }`: in `ecdh`'s `agree`, RFC 9180 §4.1 DHKEM's `ExtractAndExpand` over the shared secret, for the RFC 9180 §7.1 Table 2 pairings (P-256 and X25519 with HKDF-SHA256, P-384 with HKDF-SHA384, P-521 with HKDF-SHA512), so an HPKE KEM shared secret comes from `ecdh` directly; `kdf::derive` refuses it;
  - `kdf::Spec::OneStep { algorithm, fixed_info }`, the SP 800-56C Rev. 2 §4.1 one-step KDF with SHA-256, SHA-384 or SHA-512 (RFC 7518's Concat KDF), under HKDF's rules for `info`, output length and secret;
  - `ProfileSpec::key_agreements`, `AdmittedSelection::key_agreements`, `Admitted::key_agreements()` and `Admitted::admit_key_agreement`; ECDH on P-384, P-521 and P-256 under `preferred`, `fips1403` and `fips1402`, with X25519 under `unrestricted` too; P-384 under `cnsa1`; none under `bsi` and `cnsa2`. The one-step KDF under `unrestricted`, `preferred`, `fips1403` and `fips1402`, after the HKDFs;
  - capability cells: ECDH `NotApproved` on the 3.x line outside TLS (its security policy, p. 20), `AlgorithmTested` on A7864 on the 4.x dynamic build, `Unverified` on the 4.x static build; X25519 key agreement, and the X25519 TLS group cell, `NotApproved` on every module (FIPS 140-3 IG C.K Resolution 5; the 4.x TLS cell was `Unverified`); the one-step KDF `Approved` on the 3.x line (Table 5), `AlgorithmTested` on A7856 on the 4.x dynamic build, `Unverified` on the 4.x static build. `assert_admitted_approved` walks the key-agreement cells when `Family::KeyAgreement` is named;
  - `test_support::ecdh_shared_secret`, the test hook that returns the raw shared secret, under the `test-support` feature only;
  - Wycheproof ECDH (raw points, P-256, P-384, P-521) and X25519, RFC 7518 Appendix C, RFC 9180 Appendix A.1.1, A.3.1 and A.6.1 (through `agree` with `Spec::Dhkem`), NIST ACVP one-step KDF samples and a crypto-profile 0.9.0 sealed blob in the conformance suite.
- `tls::PeerIdentity`, an application check on the peer's end-entity certificate, added with `with_peer_identity` on `ServerVerifierBuilder` (replacing the name check) and `ClientVerifierBuilder`; it runs after every crate check. On the client verifier it can only refuse; on the server verifier it is the only identity decision, so its `Ok` admits the peer whatever server name the client connected with. `tls::PeerLeaf::uri_names` refuses a leaf whose subjectAltName rustls-webpki cannot read in full, or whose URI entries the two parsers count differently. See [decision 0009](docs/decisions/0009-peer-identity-check.md).

### Changed

- **Breaking:** `#[non_exhaustive]` on `SignatureAlgorithm`, `TlsSignatureScheme`, `CipherSuite`, `KxGroup`, `HashAlgorithm`, `MacAlgorithm`, `KdfAlgorithm`, `KeyAgreementAlgorithm`, `TlsVersion`, `Algorithm`, `Profile`, `GoverningText`, `ParseAlgorithmError`, `ParseProfileError`, `Options`, `ProfileSpec`, `Selection`, `tls::Policy` and `Resolved`; on the peer-certificate types `PeerCertificateRuleId`, `PeerCertificateRule`, `PeerKeyRule`, `RsaSizeRule`, `PeerCurve`, `PeerKey`, `CertificateSignature` and `PeerCertificateViolation`; on `csr::KeyUsage`, `csr::ExtendedKeyUsage`, `csr::CsrParams` and `test_support::Negotiated`; and on the `CryptoError::EmptyProfile` variant (decision 0012). A `match` outside the crate needs a `_` arm, and a pattern on `EmptyProfile` needs `..`; `Options`, `tls::Policy` and `csr::CsrParams` are built with `::default()` and field assignment, `Resolved` only by `resolve`, and the peer-certificate rules only by `peer_certificate_rule`. From here on a new variant of one of these enums, or a new field of one of these structs or of `EmptyProfile`, is an addition, not a breaking change; decision 0012 lists the variants that stay exhaustive.
- **Breaking:** every `ALL` (`SignatureAlgorithm::ALL` and each other algorithm enum's, and `Profile::ALL`) is a `&'static [T]` instead of a fixed-size array, so a new variant changes its length, not its type. Iterate it with `for &a in X::ALL` or `X::ALL.iter()`; `X::ALL.map(f)` becomes `X::ALL.iter().copied().map(f).collect::<Vec<_>>()`.
- **Breaking:** `PeerVerifierIdentity::Owned`'s `handshake_schemes` mask is a `u64` instead of a `u16`, so `TlsSignatureScheme` can grow past 16 schemes; the core crate fails to compile if it outgrows 64.
- **Breaking:** `signature::KeyPair::from_pkcs8` is now `from_pkcs8_der`, `pkcs8_der()` is now `to_pkcs8_der()`, and `public_key()` returns `&[u8]` instead of `Vec<u8>`.
- **Breaking:** `digest::digest` and `digest::Hasher::new` return `Result`, refusing a hash the backend does not implement with `CryptoError::Unavailable`.
- **Breaking:** `Algorithm` has new variants, `Algorithm::Mac`, `Algorithm::Kdf` and `Algorithm::KeyAgreement`; `ProfileSpec` new fields, `macs`, `kdfs` and `key_agreements`; and `Options` a new field, `cnsa1_unclassified_nss`, which admits HMAC-SHA256 and HKDF-SHA256 under `cnsa1` under CNSSP 15 (2016) Annex B ¶2b, for UNCLASSIFIED NSS data and community-of-interest separation only.
- **Breaking:** `sealbox::seal` and `sealbox::open` refuse an empty `domain` with the new `CryptoError::SealDomainEmpty`, before any key operation. The domain is the HKDF salt, and the module does not mark an HKDF call with an empty salt approved; a blob sealed under an empty domain by an earlier release no longer opens.
- **Breaking:** the sealed box is governed by a profile and built on `ecdh` and `kdf`. `sealbox::seal`, `sealbox::open`, `sealbox::PrivateKey::generate` and `sealbox::PrivateKey::from_pkcs8_der` take `&Admitted` and refuse unless the profile admits ECDH on P-384 and HKDF-SHA384, so `bsi` and `cnsa2` refuse the sealed box. `sealbox::PrivateKey` holds its key once (`to_pkcs8_der()` still returns a zeroizing copy), `PrivateKey::public_key()` returns the raw public key (the uncompressed point), and the new `PrivateKey::recipient()` returns the `sealbox::PublicKey` to seal to. `sealbox::PublicKey::from_spki_der` and `from_pem` refuse a key whose point is not uncompressed; the 4.x module had decoded a hybrid point. The wire format is unchanged: a blob sealed by 0.9.0 opens.
- `ParseAlgorithmError`'s `Display` reads "unknown algorithm name …"; it no longer says "signature", because `KeyAgreementAlgorithm` parses with it too.
- `Options`' `Display` names each option set, joined with ", "; the existing strings are unchanged.

## [0.9.0] - 2026-10-30

### Added

- crates.io metadata, per-crate licence files, and the test-support RSA-8192 key packaged inside the core crate.
- `tls::crypto_provider`, and every builder that calls it, refuses a policy that lists a version with no suite, no key-exchange group usable at it, or no signature scheme a suite at it can sign with (TLS 1.2 has no ML-KEM or hybrid group and no ML-DSA, and fixes ECDSA or RSA authentication per suite; TLS 1.3 has no RSA PKCS#1 v1.5 handshake signature), as `CryptoError::PolicyVersionUnusable { version, family }`. New public helpers: `KxGroup::usable_in`, `TlsSignatureScheme::usable_in`, `CipherSuite::signs_with`.
- Opt-in `Options::peer_certificates_match_profile` checks peer leaf keys and selected certificate paths against cited profile rules. Strict TLS builders install matching crate-owned verifier handles and report typed refusals. See [decision 0007](docs/decisions/0007-peer-certificate-rules.md).
- Both backends' build scripts refuse a build that does not link their bundled AWS-LC FIPS source build (the reported library name must be the bundled, version-prefixed one), so `MODULE` and `certificate()` always describe the linked module. Set `AWS_LC_FIPS_SYS_USE_SYSTEM=0` on a host with a system AWS-LC.
- The `crypto-profile-awslc3` backend, in its own workspace and lockfile, builds AWS-LC 3.6.0 from the FIPS 3.x line; its 3.1.0 release has CMVP certificates #5314 (static) and #5298 (dynamic). Both backends expose `awslc_version()` separately from certificate data and share provider and backend-body source. Exactly one backend can enter a build graph.
- Profile resolution records unavailable line entries in `Selection::excluded` and `Resolved::excluded`; an empty family is refused. On 3.x, `cnsa2` is refused and ML-DSA is excluded from the applicable successful profiles. Approval remains a separate check.
- The core crate `crypto-profile`, with no aws-lc dependency:
  - exhaustive algorithm types: `SignatureAlgorithm`, `TlsSignatureScheme`, `CipherSuite`, `KxGroup`, `HashAlgorithm`, `TlsVersion` and `Algorithm`, with literal IANA codepoints (`iana()`), the canonical TLS signature-scheme order (`TlsSignatureScheme::preference`) and X.509 signature OIDs (`signature_oid()`), and `FromStr` and `Display` for `SignatureAlgorithm`;
  - the capability model: `Module { line, linkage }`, `certificate()` and `capability()`, where each 3.x cell cites the AWS-LC FIPS 3.1.0 security policy of its own certificate, #5314 (static) or #5298 (dynamic): an `Approved` cell cites Table 5 (pp. 8-11), a `NotApproved` cell cites its absence from Tables 5-8, and the hybrid key-exchange groups and TLS 1.3 are `Unverified`, with no source; every 4.x static cell is `Unverified`, and each 4.x dynamic cell is `Approval::AlgorithmTested`, citing the one AWS-LC FIPS 4.0.0 CAVP certificate that shows every operation it needs, or `Unverified` (decision record 0004); `AlgorithmTested`, like `Unverified`, is never approved;
  - the seven profiles `unrestricted`, `preferred`, `cnsa2`, `cnsa1`, `bsi`, `fips1403` and `fips1402` as the public `ProfileSpec` constants `UNRESTRICTED`, `PREFERRED`, `CNSA2`, `CNSA1`, `BSI`, `FIPS1403` and `FIPS1402`, each entry cited in its constant's doc comment (0.x API: names and contents may change before 1.0); `Profile`, with `Profile::ALL`, `as_str`, `spec` and `governing_text`, `FromStr` and `Display` over exact names, and `ParseProfileError` for a name that is not a profile; and `GoverningText`;
  - `Options` and post-quantum key exchange required (`pq_key_exchange_required`), with `Display` and `KxGroup::is_post_quantum`;
  - `crypto_profile::profile::select`, the backend-independent half of resolution, which returns a `Selection` with line exclusions recorded after Options and refuses an empty family;
  - typed errors: `CryptoError`, with `Unavailable(Algorithm)`, `PolicyEmpty(Family)`, `PolicyDuplicate(Algorithm)`, `PolicyDrift`, `EmptyProfile`, `KeyNotInProfile` and `NotApproved`, `Family::KeyAlgorithm`, and the typed causes `CsrError` and `TlsError`;
  - the sealed box's version-1 framing (`sealbox_wire`);
  - the conformance suite behind the `conformance` feature, run by every backend through `conformance_tests!`, including the profile golden tables and distinction handshakes.
- The backend `crypto-profile-awslc4`, on the AWS-LC FIPS 4.x module through aws-lc-rs 1.18.2:
  - `MODULE`, with the linkage read from the build; the build fails if aws-lc-rs does not report it;
  - `digest`, `random`, `aead` (AES-256-GCM with module-chosen nonces), `sealbox` (P-384 ECDH, HKDF-SHA384, AES-256-GCM), `signature` (key generation, signing, verification and the SubjectPublicKeyInfo shape check) and `csr` (PKCS#10 requests with a DN, DNS, IP and URI SANs, EKU and key usage, signed by the request's own key);
  - `tls`: `Policy`, `crypto_provider`, the client and server builders, `install_default`, `assert_provider_matches`, `load_private_key` and the certificate-verifier builders, over the crate's own provider with TLS 1.2 enabled; a policy's signature schemes are a set, carried in `TlsSignatureScheme::preference` order, and a duplicate entry in any list is refused with `PolicyDuplicate`; the verification tables and key providers rustls takes by `'static` reference are cached per distinct set of signature schemes, at most 2^n − 1 for the n schemes in the inventory (2,047 today);
  - `fips`: `assert_fips_module`, `assert_fips_client_config`, `assert_fips_server_config`, `certificate` and `approval`;
  - the signing-scheme constraint: a key loaded through a provider built from a `tls::Policy` (the builders' `with_single_cert` and `with_client_auth_cert`, and `tls::load_private_key`, which now takes the policy) signs only with a scheme that is in both the peer's offer and `signature_schemes`, and when none is, a server's handshake fails and a client sends an empty Certificate (a failure only if the server requires client authentication); `Resolved::certified_key`, which also refuses a key the profile does not admit and a chain whose end-entity certificate does not carry the key (`TlsError::KeyMismatch`); and `assert_provider_matches` refuses a provider whose key provider is not the policy's;
  - `resolve`, `Resolved` and `Resolved::admit_key`, and `assert_module_approves`, which refuses with `NotFips` outside FIPS mode, with `PolicyEmpty` for an empty family, and then every cell that is not `Approved`;
  - `test_support::handshake_with_ca`, a handshake whose CA key algorithm the caller chooses;
  - `test_support::FIPS_LIBRARY`, the FIPS module's crypto library name, taken from aws-lc-rs's link metadata by the build script; the build fails if aws-lc-rs does not report it or reports anything but the bundled, version-prefixed name;
  - the `rustls` re-export, and `rcgen` under the `test-support` feature.
- Known-answer tests: Wycheproof (ECDSA, Ed25519, RSA PKCS#1 v1.5 SHA-384, ML-DSA-87, AES-GCM), NIST CAVP SHA-2, RFC 8032 and a sealed-box version-1 blob.
- Documentation: `docs/usage.md`, `docs/profiles.md`, `CONTRIBUTING.md` (with the Developer Certificate of Origin and the AI-assistance disclosure), `SECURITY.md`, decision records 0001 to 0004, the pull request template, `CODE_OF_CONDUCT.md` (the Contributor Covenant 2.1) and issue templates.
- `docs/sources.md`: every document a profile, citation or capability cell depends on, with the edition followed, the issuer's link and the SHA-256 of the copy the maintainers read; linked from `docs/profiles.md` and the README.
- The crate's own rustls `CryptoProvider`: written once in core and emitted by the core `provider!` macro, which `crypto-profile-awslc4` instantiates (decision record 0005). The cryptography is the module's through aws-lc-rs; rustls supplies the TLS protocol.
- QUIC on the provider's TLS 1.3 suites: packet and header protection and RFC 9001's packet limits, ported from rustls's built-in aws-lc-rs provider, so `rustls::quic` connections (HTTP/3, for example) keep working as they did on rustls's own suites; tested against RFC 9001 Appendix A, a QUIC handshake and rustls's suites (#12).
- `KxGroup::Secp384r1MlKem1024` (SecP384r1MLKEM1024, 0x11ED, RFC 10024), `Unverified` on every module, in `unrestricted`, `preferred` and `fips1403`.
- `crypto-profile-awslc4/tests/differential.rs`, which checks the provider against rustls's built-in one; `ci/shipped-graph.sh`, which refuses a stock rustls provider in the shipped graph; and the OpenSSL interop test (`crypto-profile-awslc4/tests/openssl_interop.rs`, `ci/openssl-interop.sh`), which negotiates SecP384r1MLKEM1024 with OpenSSL 3.5 in both directions.
- CI tests both backends on Linux x86_64 (static and dynamic), Linux aarch64 (static) and macOS arm64 (dynamic).
- From 0.9.1, releases are cut from a `v*` tag on `main` and published through crates.io trusted publishing. Each `.crate` gets a build-provenance attestation, made only after the file crates.io serves matches the package built from the tagged commit. 0.9.0 is published by hand, because trusted publishing cannot make a crate's first release.

### Changed

- `crypto-profile-awslc4` builds rustls with `std` and `tls12` only, so the re-exported `rustls` no longer has a built-in provider: `rustls::crypto::aws_lc_rs` (with its `Ticketer`, `hpke`, `cipher_suite`, `kx_group` and `sign`) and `rustls::crypto::default_fips_provider` are gone, and `ClientConfig::builder()`, `ServerConfig::builder()` and the WebPKI verifiers' `builder()` no longer install a provider: they panic unless one is installed as the process default (`tls::install_default`), or the features another crate in the build unifies onto rustls name exactly one of `aws_lc_rs` and `ring` and not `custom-provider`, in which case they install rustls's stock provider.

### Known issues

- On aarch64 (Linux and macOS, both module lines), the AWS-LC FIPS module refuses two valid Wycheproof P-256/SHA-256 signatures: s = 2^128 and s = n - 2^128 ([#24](https://github.com/crypto-profile/crypto-profile/issues/24), reported as [aws/aws-lc#3715](https://github.com/aws/aws-lc/issues/3715)).
  - The refusal fails closed, and no invalid signature is accepted on any target.
  - An honest signature takes either value with probability about 2^-255.
  - The conformance suite pins both refusals, so it fails once a module fixes them.

### Known 0.x items

These are known and left for a later 0.x release, which may change them incompatibly:

- `CryptoError`'s `Display` writes algorithms, approvals and causes with their `Debug` form (for example `Protocol(Tls13)` and `AlgorithmTested { cavp: "…" }`), so operator-facing messages carry Rust syntax.
- `Options` has a public field and is not `#[non_exhaustive]`, so adding an option is a breaking change.
