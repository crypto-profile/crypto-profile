# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor version may change the API. The three crates share one version and are released together.

### Added

- HMAC under a profile (#31), the first family governed outside TLS (decision 0008):
  - `MacAlgorithm` (HMAC-SHA256, HMAC-SHA384, HMAC-SHA512), with `hash()` and `tag_len()`;
  - capability cells: `Approved` on the 3.x line (Table 5 of each certificate's security policy), `AlgorithmTested` on A7855 on the 4.x dynamic build and on A7902 on the 4.x static build;
  - `admit(profile, options)`, which never refuses, and `Admitted`, both independent of `resolve`; `Admitted` is read-only (`profile()`, `options()`, `macs()`, `excluded()`) and built only by `admit`; `Admitted::admit_mac`, which refuses a MAC the module line lacks with `CryptoError::Unavailable`; `assert_admitted_approved(&admitted, families)`, separate from `assert_module_approves`, which checks the families outside TLS the caller names (Mac, then Kdf, then KeyAgreement, then Aead, then Hash, then Signature), refuses a TLS family with `CryptoError::FamilyNotAdmitted`, and approves nothing for an empty list; in the core crate, `select_admitted` and `AdmittedSelection`;

  - `CryptoError::NotInProfile`, for any algorithm outside TLS a profile does not admit, `CryptoError::MacKeyLength` and `CryptoError::MacVerify`;
  - Wycheproof HMAC-SHA256, HMAC-SHA384 and HMAC-SHA512 in the conformance suite.
- HKDF under a profile (#32), the second family governed outside TLS (decision 0010):
  - `KdfAlgorithm` (HKDF-SHA256, HKDF-SHA384, HKDF-SHA512), with `hash()` and `max_output_len()`;
  - capability cells: `Approved` on the 3.x line (Table 5 of each certificate's security policy), `AlgorithmTested` on A7855 on the 4.x dynamic build and on A7902 on the 4.x static build;
  - `Admitted::kdfs()` and `Admitted::admit_kdf`; `assert_admitted_approved` walks the KDF cells when `Family::Kdf` is named, and first refuses a profile that admits KDFs and an empty `info` (`unrestricted`) with `CryptoError::KdfInfoMayBeEmpty`; in the core crate, `AdmittedSelection::kdfs` and `kdf_info_may_be_empty`;
  - `kdf::derive` with `kdf::Spec::Hkdf`, and `kdf::DerivedKey`: RFC 5869 extract-then-expand in one call, with no public extract; an absent or empty salt is HashLen zeros; an empty `info` is refused under every profile but `unrestricted`; output 1 to 255 × HashLen bytes; an empty secret is refused; the derived key is zeroized on drop;
  - `CryptoError::KdfOutputLength`, `CryptoError::KdfSecretEmpty`, `CryptoError::KdfInfoEmpty` and `CryptoError::KdfInfoMayBeEmpty`, whose `Display` names the KDF generically ("a KDF output of …", "the KDF secret is empty", "an empty KDF info");
  - RFC 5869 Appendix A cases 1-3 and Wycheproof HKDF-SHA256, HKDF-SHA384 and HKDF-SHA512 in the conformance suite.
- The 0.10.0 API shape (#33, decision 0012):
  - `KeyAgreementAlgorithm` (ECDH on P-256, P-384 and P-521, and X25519), with `ALL`, `as_str`, `Display` and `FromStr`, and `Algorithm::KeyAgreement`; `KdfAlgorithm::OneStepSha256`, `OneStepSha384` and `OneStepSha512` (SP 800-56C Rev. 2 §4.1), whose `max_output_len()` is 2^30 bytes;
  - `kdf::Spec`, `#[non_exhaustive]`, with `Spec::Hkdf`; a `Spec` whose algorithm does not match its variant is refused with `CryptoError::KdfSpecMismatch`, before admission;
  - `Family::Mac`, `Family::Kdf` and `Family::KeyAgreement`;
  - `CryptoError::KdfSpecMismatch`, `CryptoError::KeyAgreementPeerKey`, `CryptoError::KeyAgreementPrivateKey` and `CryptoError::FamilyNotAdmitted`.
- ECDH and the one-step KDF under a profile (#33, decision 0011):
  - `ecdh::EphemeralKey` (`generate`, `algorithm`, `public_key`, and `agree`, which consumes the key) and `ecdh::StaticKey` (`from_pkcs8_der`, `from_scalar`, `algorithm`, `public_key`, `agree`): one-pass Diffie-Hellman in both roles on P-256, P-384, P-521 and X25519, each agreement completing into `kdf` in the same call, so the shared secret never leaves the crate. A peer key must be an uncompressed point (or 32 bytes for X25519); compressed and hybrid points and SubjectPublicKeyInfos are refused with `CryptoError::KeyAgreementPeerKey` before the module sees them, and the module validates the rest. A static key is imported only, from DER or a raw private key of exactly the field length; `CryptoError::KeyAgreementPrivateKey` refuses anything else. `StaticKey::from_pkcs8_der` takes a P-256, P-384 or P-521 key as an RFC 5958 §2 `PrivateKeyInfo` of version v1 (privateKeyAlgorithm `id-ecPublicKey` with the key's namedCurve per RFC 5480 §2.1.1, privateKey an `ECPrivateKey`, optional `[0]` attributes) or as an RFC 5915 §3 `ECPrivateKey` with its parameters. The `ECPrivateKey` holds version 1, a privateKey of exactly 32, 48 or 66 bytes, optional parameters naming the key's curve, and an optional publicKey that must be the key's own uncompressed point (RFC 5915 §3, RFC 5480 §2.2). The crate checks this structure itself, before the module parses the key. Three refusals go beyond the RFC text: fields and versions the RFCs do not define (their ASN.1 extension markers); BER, though RFC 5958 §2 says receivers MUST support it and RFC 5915 §4 says SHOULD; and `id-ecDH` and `id-ecMQV`. An X25519 key is imported raw;
  - `kdf::Spec::Dhkem { algorithm }`: in `ecdh`'s `agree`, RFC 9180 §4.1 DHKEM's `ExtractAndExpand` over the shared secret, for the RFC 9180 §7.1 Table 2 pairings (P-256 and X25519 with HKDF-SHA256, P-384 with HKDF-SHA384, P-521 with HKDF-SHA512), so an HPKE KEM shared secret comes from `ecdh` directly; `kdf::derive` refuses it;
  - `kdf::Spec::OneStep { algorithm, fixed_info }`, the SP 800-56C Rev. 2 §4.1 one-step KDF with SHA-256, SHA-384 or SHA-512 (RFC 7518's Concat KDF), under HKDF's rules for `info`, output length and secret;
  - `ProfileSpec::key_agreements`, `AdmittedSelection::key_agreements`, `Admitted::key_agreements()` and `Admitted::admit_key_agreement`; ECDH on P-384, P-521 and P-256 under `preferred`, `fips1403` and `fips1402`, with X25519 under `unrestricted` too; P-384 under `cnsa1`; none under `bsi` and `cnsa2`. The one-step KDF under `unrestricted`, `preferred`, `fips1403` and `fips1402`, after the HKDFs;
  - capability cells: ECDH `NotApproved` on the 3.x line outside TLS (its security policy, p. 20), `AlgorithmTested` on A7864 on the 4.x dynamic build and on A7919 on the 4.x static build; X25519 key agreement `NotApproved` on every module (FIPS 140-3 IG C.K Resolution 5); the one-step KDF `Approved` on the 3.x line (Table 5), `AlgorithmTested` on A7856 on the 4.x dynamic build and on A7903 on the 4.x static build. `assert_admitted_approved` walks the key-agreement cells when `Family::KeyAgreement` is named;
  - `test_support::ecdh_shared_secret`, the test hook that returns the raw shared secret, under the `test-support` feature only;
  - Wycheproof ECDH (raw points, P-256, P-384, P-521) and X25519, RFC 7518 Appendix C, RFC 9180 Appendix A.1.1, A.3.1 and A.6.1 (through `agree` with `Spec::Dhkem`), NIST ACVP one-step KDF samples and a crypto-profile 0.9.0 sealed blob in the conformance suite.
- AEAD under a profile (#44, decision 0013):
  - `AeadAlgorithm` (AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305), `#[non_exhaustive]`, with `ALL`, `as_str`, `Display`, `FromStr`, `key_len()` and `max_plaintext_len()`, and `Algorithm::Aead` and `Family::Aead`;
  - `aead::Key`: `new(&admitted, algorithm, key)`, `algorithm()`, `seal_in_place` and `open_in_place`. A seal never takes a caller's nonce: AES-GCM's comes from the module's random-nonce seal, ChaCha20-Poly1305's from the module's DRBG. Each key refuses its 2^32 + 1th seal (SP 800-38D §8.3), and a plaintext over 2^36 − 32 bytes (AES-GCM) or 274,877,906,879 bytes (ChaCha20-Poly1305), before the module. Tags are 16 bytes. `Key` is not `Clone`;

  - `test_support::aead_set_invocations`, the test hook that sets a key's seal count, under the `test-support` feature only;
  - Wycheproof AES-128-GCM and ChaCha20-Poly1305 beside AES-256-GCM in the conformance suite.
- Hashing under a profile, with SHA-3 (#45, decision 0014):

  - `ProfileSpec::hashes`, `AdmittedSelection::hashes`, `Admitted::hashes()` and `Admitted::admit_hash`: SHA-512, SHA-384 and SHA-256 under `preferred`; with SHA3-512, SHA3-384 and SHA3-256 under `unrestricted`, `bsi`, `fips1403` and `fips1402`; SHA-384 and SHA-512 under `cnsa2`; SHA-384 under `cnsa1`, and SHA-256 too with `Options::cnsa1_unclassified_nss`. `assert_admitted_approved` walks the hash cells, after the AEAD cells, when `Family::Hash` is named;
  - `digest::Hasher::algorithm()`; `Hasher` is not `Clone`, and its `Debug` names the algorithm only;

  - `SignatureAlgorithm::Rsa2048Sha384Pss`, `Rsa3072Sha384Pss` and `Rsa4096Sha384Pss` (`rsa2048-sha384-pss`, `rsa3072-sha384-pss`, `rsa4096-sha384-pss`): RSASSA-PSS with SHA-384, MGF1 with SHA-384 and a 48-byte salt, outside TLS only; `signature_oid()` is `id-RSASSA-PSS`;

  - capability cells: RSA-PSS `Approved` on the 3.x line (Table 5), `AlgorithmTested` on A7873 (4.x dynamic) and A7912 (4.x static);

- `tls::CertificateKey`, a TLS certificate key governed by the profile's TLS key list (#57, decision 0016): `generate(&resolved, alg)` and `from_pkcs8_der(&resolved, alg, der)` refuse an algorithm not in `Resolved::keys` with `CryptoError::KeyNotInProfile`, then one the module line lacks with `CryptoError::Unavailable`, and `from_pkcs8_der` then refuses, with `CryptoError::SignaturePrivateKey`, any structure or key `signature::KeyPair::from_pkcs8_der` refuses; `algorithm()`, `public_key()` and `to_pkcs8_der()`. It has no `sign`; it signs through the TLS key provider with the policy's TLS schemes (decision 0016, residual 2). It is not `Clone`, and its `Debug` prints the algorithm only. Every TLS key of every profile now has a governed route, `bsi`'s and P-521 with SHA-384 under `preferred` and `fips1403` among them.
- `test_support::issue(ca, key: tls::CertificateKey)`, behind the `test-support` feature, issues a leaf for a `CertificateKey` under a fresh CA.
- `tls::PeerIdentity`, an application check on the peer's end-entity certificate, added with `with_peer_identity` on `ServerVerifierBuilder` (replacing the name check) and `ClientVerifierBuilder`; it runs after every crate check. On the client verifier it can only refuse; on the server verifier it is the only identity decision, so its `Ok` admits the peer whatever server name the client connected with. `tls::PeerLeaf::uri_names` refuses a leaf whose subjectAltName rustls-webpki cannot read in full, or whose URI entries the two parsers count differently. See [decision 0009](docs/decisions/0009-peer-identity-check.md).

### Changed

- The `tls::PeerIdentity` example in `docs/usage.md` §6 is a doctest on `tls::PeerIdentity`, compiled on both backends (#38).
- `ci/quality.sh mutants-diff`: the pre-PR mutation gate runs over the branch's changes only; the full set stays a weekly CI run and a pre-release check.
- **Breaking:** `#[non_exhaustive]` on `SignatureAlgorithm`, `TlsSignatureScheme`, `CipherSuite`, `KxGroup`, `HashAlgorithm`, `MacAlgorithm`, `KdfAlgorithm`, `KeyAgreementAlgorithm`, `TlsVersion`, `Algorithm`, `Profile`, `GoverningText`, `ParseAlgorithmError`, `ParseProfileError`, `Options`, `ProfileSpec`, `Selection`, `tls::Policy` and `Resolved`; on the peer-certificate types `PeerCertificateRuleId`, `PeerCertificateRule`, `PeerKeyRule`, `RsaSizeRule`, `PeerCurve`, `PeerKey`, `CertificateSignature` and `PeerCertificateViolation`; on `csr::KeyUsage`, `csr::ExtendedKeyUsage`, `csr::CsrParams` and `test_support::Negotiated`; and on the `CryptoError::EmptyProfile` variant (decision 0012). A `match` outside the crate needs a `_` arm, and a pattern on `EmptyProfile` needs `..`; `Options`, `tls::Policy` and `csr::CsrParams` are built with `::default()` and field assignment, `Resolved` only by `resolve`, and the peer-certificate rules only by `peer_certificate_rule`. From here on a new variant of one of these enums, or a new field of one of these structs or of `EmptyProfile`, is an addition, not a breaking change; decision 0012 lists the variants that stay exhaustive.
- **Breaking:** every `ALL` (`SignatureAlgorithm::ALL` and each other algorithm enum's, and `Profile::ALL`) is a `&'static [T]` instead of a fixed-size array, so a new variant changes its length, not its type. Iterate it with `for &a in X::ALL` or `X::ALL.iter()`; `X::ALL.map(f)` becomes `X::ALL.iter().copied().map(f).collect::<Vec<_>>()`.
- **Breaking:** `PeerVerifierIdentity::Owned`'s `handshake_schemes` mask is a `u64` instead of a `u16`, so `TlsSignatureScheme` can grow past 16 schemes; the core crate fails to compile if it outgrows 64.
- **Breaking:** `signature::KeyPair::from_pkcs8` is now `from_pkcs8_der`, `pkcs8_der()` is now `to_pkcs8_der()`, and `public_key()` returns `&[u8]` instead of `Vec<u8>`.
- **Breaking:** signature key generation, key import and verification are governed by a profile (decision 0015). `signature::KeyPair::generate`, `KeyPair::from_pkcs8_der` and `signature::verify` take `&Admitted` and refuse an algorithm the profile does not admit outside TLS with `CryptoError::NotInProfile`, or one the module line lacks with `CryptoError::Unavailable`. A `KeyPair` holds the module's parsed key, so `sign` no longer parses it on every call, and is not `Clone`; `to_pkcs8_der()` returns `Result<Zeroizing<Vec<u8>>, CryptoError>`, the module's canonical encoding, not the bytes imported. `from_pkcs8_der` takes only the DER structure each key type's RFCs define and refuses trailing bytes, a second key, misordered attributes, an attribute whose OBJECT IDENTIFIER is not a valid X.690 §8.19 encoding, a version that does not match its fields, explicit EC parameters, an ML-DSA-87 expanded key alone, an ML-DSA-87 expanded key that is not the one its seed expands to and a carried public key that is not the key's own, with `CryptoError::SignaturePrivateKey` where it returned `CryptoError::PrivateKey`. `verify` takes the raw public key only and refuses a SubjectPublicKeyInfo, a compressed point and a key of the wrong length with `CryptoError::SignaturePublicKey`; an RSA public key of the wrong size or exponent is `SignaturePublicKey` where it was `CryptoError::Verify`. `SignatureAlgorithm::tls_scheme()` returns `Option<TlsSignatureScheme>`, `None` for RSA-PSS. `tls::load_private_key` and the rustls builders load an ML-DSA-87 key through the checks `from_pkcs8_der` applies, so they refuse what it refuses, where they took it: an expanded key that is not the one its seed expands to, a carried public key that is not the key's own, an expanded key alone, and a structure RFC 9881 does not define.
- **Breaking:** `tls::load_private_key` and the rustls builders refuse ML-DSA-44 and ML-DSA-65 keys, which no profile can sign with; they load ML-DSA-87 keys only, through the checks `signature::KeyPair::from_pkcs8_der` applies (#46).
- **Breaking:** `tls::load_private_key`, `Resolved::certified_key` and the rustls builders check every private key's structure for its form before the module parses it, as `signature::KeyPair::from_pkcs8_der` does (#48, decision 0015): a `Pkcs8` ECDSA, Ed25519 or RSA key as `from_pkcs8_der` takes it, a `Sec1` key as one RFC 5915 §3 `ECPrivateKey` on P-256, P-384 or P-521 with parameters naming its curve, a `Pkcs1` key as one two-prime RFC 8017 A.1.2 `RSAPrivateKey`. They refuse what they loaded: a key followed by other bytes, two concatenated keys, misordered attributes, an attribute whose OBJECT IDENTIFIER is malformed, a version that does not match its fields, an undefined trailing field, explicit EC parameters, an EC private key shorter or longer than its curve's length, a compressed EC public key carried in the key (and, on the 4.x line, a hybrid one), a `Sec1` key without parameters and an ECDSA PKCS#8 key passed as `Sec1`; `openssl ec -conv_form uncompressed` re-encodes a compressed key into a SEC 1 key that loads, and `openssl pkcs8 -topk8 -nocrypt` after it gives the PKCS#8 form. An RSA key must be 2048, 3072 or 4096 bits with public exponent 65537, where any size from 2048 to 8,192 bits and any odd exponent the module took was loaded. A peer's key values are checked by rustls and rustls-webpki, as before.
- **Breaking:** `csr::generate_csr` takes `&tls::CertificateKey` and returns the PEM request only (`Result<String, CryptoError>`), where it took a `SignatureAlgorithm` and returned a new `signature::KeyPair` with the request; that key signed any message and exported under no profile (#57, decision 0016). Generate the key with `tls::CertificateKey::generate(&resolved, alg)`, which refuses an algorithm the profile's TLS key list does not hold, and keep it to request again.
- **Breaking:** `Resolved::certified_key` takes `&tls::CertificateKey`, where it took `&signature::KeyPair` (#57).
- **Breaking:** `test_support::Pki::key` (feature `test-support`) is a `tls::CertificateKey`, where it was a `signature::KeyPair`; `test_support::handshake_certified` generates its leaf under the server's `Resolved`, so it refuses a key that `Resolved`'s TLS key list does not hold (#57).
- **Breaking:** `CryptoError::PrivateKey` is removed (#58). No operation produces it any more: each key import refuses with its own error (`CryptoError::SignaturePrivateKey`, `CryptoError::KeyAgreementPrivateKey`, `CryptoError::SealPrivateKey`), and `tls::load_private_key` with `CryptoError::Tls(TlsError::PrivateKey)`, as before.
- `capability()` reports Ed25519 (`Algorithm::Signature(SignatureAlgorithm::Ed25519)` and `Algorithm::Scheme(TlsSignatureScheme::Ed25519)`) on the 3.x static build (#5314) as `NotApproved`: its Approved Services table lists no EdDSA signature service. No TLS outcome of `assert_module_approves` changes.
- **Breaking:** `Algorithm` has new variants, `Algorithm::Mac`, `Algorithm::Kdf`, `Algorithm::KeyAgreement` and `Algorithm::Aead`; `ProfileSpec` new fields, `macs`, `kdfs`, `key_agreements`, `aeads`, `hashes` and `signatures`; and `Options` a new field, `cnsa1_unclassified_nss`, which admits HMAC-SHA256, HKDF-SHA256, SHA-256 hashing and RSA-2048 signatures under `cnsa1` under CNSSP 15 (2016) Annex B ¶2b, for UNCLASSIFIED NSS data and community-of-interest separation only.
- **Breaking:** `sealbox::seal` and `sealbox::open` refuse an empty `domain` with the new `CryptoError::SealDomainEmpty`, before any key operation. The domain is the HKDF salt, and the module does not mark an HKDF call with an empty salt approved; a blob sealed under an empty domain by an earlier release no longer opens.
- **Breaking:** the sealed box is governed by a profile and built on `ecdh` and `kdf`. `sealbox::seal`, `sealbox::open`, `sealbox::PrivateKey::generate` and `sealbox::PrivateKey::from_pkcs8_der` take `&Admitted` and refuse unless the profile admits ECDH on P-384, HKDF-SHA384 and AES-256-GCM, so `bsi` and `cnsa2` refuse the sealed box. `sealbox::PrivateKey` holds its key once (`to_pkcs8_der()` still returns a zeroizing copy), `PrivateKey::public_key()` returns the raw public key (the uncompressed point), and the new `PrivateKey::recipient()` returns the `sealbox::PublicKey` to seal to. `PrivateKey::generate` and `seal` report a key-generation failure as `CryptoError::KeyGeneration(Algorithm::KeyAgreement(KeyAgreementAlgorithm::EcdhP384))` instead of `CryptoError::Primitive`. `sealbox::PublicKey::from_spki_der` and `from_pem` refuse a key whose point is not uncompressed; the 4.x module had decoded a hybrid point. `PrivateKey::from_pkcs8_der` takes exactly the P-384 keys `ecdh::StaticKey::from_pkcs8_der` takes, and refuses a key followed by other bytes, a `PrivateKeyInfo` of version v2 or with a `[1]` publicKey, and any field RFC 5958 §2 or RFC 5915 §3 does not define. The wire format is unchanged: a blob sealed by 0.9.0 opens.
- The 4.x static build's cells are sourced from its own CAVP certificates, A7886-A7923, under decision 0004 §2, instead of all being `Unverified`: every cell has the dynamic build's verdict, on the static counterpart of its certificate (A7902, A7903, A7912, A7919 and A7887). `assert_module_approves` and `assert_admitted_approved` still refuse the same algorithms on 4.x, now reporting `AlgorithmTested` where they reported `Unverified`. The 4.x status text cites the CMVP Modules In Process list (last updated 11/2/2026): both 4.x modules are in "Comment Resolution - Lab (10/22/2026)".
- **Breaking:** `aead::Aes256GcmKey` and `aead::KEY_LEN` are removed: `aead::Key::new(&admitted, AeadAlgorithm::Aes256Gcm, &key)` and `AeadAlgorithm::key_len()` replace them. The sealed box also refuses unless the profile admits AES-256-GCM; every profile that admitted it does, and a blob sealed by 0.9.0 still opens.
- **Breaking:** `digest::digest(&admitted, h, data)` and `digest::Hasher::new(&admitted, h)` return `Result` and take an `Admitted`: they refuse a hash the profile does not admit with `CryptoError::NotInProfile`, so `cnsa2` refuses SHA-256, and a hash the backend does not implement with `CryptoError::Unavailable`. `digest::sha256` and `digest::sha256_hex` are removed: call `digest::digest(&admitted, HashAlgorithm::Sha256, data)` and convert or format the digest yourself.
- `capability()` reports the X25519 TLS group cell (`Algorithm::Kx(KxGroup::X25519)`) on the 4.x line as `NotApproved` (FIPS 140-3 IG C.K Resolution 5) instead of `Unverified`.
- `ParseAlgorithmError`'s `Display` reads "unknown algorithm name …"; it no longer says "signature", because `KeyAgreementAlgorithm` parses with it too.
- `Options`' `Display` names each option set, joined with ", "; the existing strings are unchanged.

## [0.9.0] - 2026-10-30

### Added

- crates.io metadata, per-crate licence files, and the test-support RSA-8192 key packaged inside the core crate.
- `tls::crypto_provider`, and every builder that calls it, refuses a policy that lists a version with no suite, no key-exchange group usable at it, or no signature scheme a suite at it can sign with (TLS 1.2 has no ML-KEM or hybrid group and no ML-DSA, and fixes ECDSA or RSA authentication per suite; TLS 1.3 has no RSA PKCS#1 v1.5 handshake signature), as `CryptoError::PolicyVersionUnusable { version, family }`. New public helpers: `KxGroup::usable_in`, `TlsSignatureScheme::usable_in`, `CipherSuite::signs_with`.
- Opt-in `Options::peer_certificates_match_profile` checks peer leaf keys and selected certificate paths against cited profile rules. Strict TLS builders install matching crate-owned verifier handles and report typed refusals. See [decision 0007](docs/decisions/0007-peer-certificate-rules.md).
- Both backends' build scripts refuse a build that does not link their bundled AWS-LC FIPS source build (the reported library name must be the bundled, version-prefixed one), so `MODULE` and `certificate()` always describe the linked module. Set `AWS_LC_FIPS_SYS_USE_SYSTEM=0` on a host with a system AWS-LC.
- The `crypto-profile-awslc3` backend, in its own workspace and lockfile, builds AWS-LC 3.6.0 from the FIPS 3.x line; its 3.1.0 release has CMVP certificates #5314 (static) and #5298 (dynamic). Both backends expose `awslc_version()` separately from certificate data and share provider and backend-body source. Exactly one backend can enter a build graph.
- Profile resolution records unavailable line entries in `Selection::excluded` and `Resolved::excluded`; an empty family is refused. On 3.x, `cnsa2` is refused and ML-DSA is excluded from the applicable successful profiles. Approval remains a separate check.

### Changed

- `crypto-profile-awslc4` builds rustls with `std` and `tls12` only, so the re-exported `rustls` no longer has a built-in provider: `rustls::crypto::aws_lc_rs` (with its `Ticketer`, `hpke`, `cipher_suite`, `kx_group` and `sign`) and `rustls::crypto::default_fips_provider` are gone, and `ClientConfig::builder()`, `ServerConfig::builder()` and the WebPKI verifiers' `builder()` no longer install a provider: they panic unless one is installed as the process default (`tls::install_default`), or the features another crate in the build unifies onto rustls name exactly one of `aws_lc_rs` and `ring` and not `custom-provider`, in which case they install rustls's stock provider.

### Known issues

- On aarch64 (Linux and macOS, both module lines), the AWS-LC FIPS module refuses two valid Wycheproof P-256/SHA-256 signatures: s = 2^128 and s = n - 2^128 ([#24](https://github.com/crypto-profile/crypto-profile/issues/24), reported as [aws/aws-lc#3715](https://github.com/aws/aws-lc/issues/3715)).
  - The refusal fails closed, and no invalid signature is accepted on any target.
  - An honest signature takes either value with probability about 2^-255.
  - The conformance suite pins both refusals, so it fails once a module fixes them.

### Known 0.x items

These are known and left for a later 0.x release, which may change them incompatibly:

- `CryptoError`'s `Display` writes algorithms, approvals and causes with their `Debug` form (for example `Protocol(Tls13)` and `AlgorithmTested { cavp: "…" }`), so operator-facing messages carry Rust syntax.
- `Options` has a public field and is not `#[non_exhaustive]`, so adding an option is a breaking change.
