# 0013: AEAD under a profile

Date: 2026-11-03. Status: accepted.

## Context

Before this decision `aead` offered AES-256-GCM alone, through `Aes256GcmKey::new(&[u8; 32])`, which took no `Admitted`: no profile governed it, and `sealbox` checked its ECDH and HKDF against the profile but not its AEAD. Five profiles admit AES-128-GCM and `unrestricted` admits ChaCha20-Poly1305, so the crate could not offer either under a profile. Nothing counted seals: SP 800-38D §8.3 (p. 21) limits the authenticated-encryption function to 2^32 invocations per key when the IV comes from a random bit generator, and AWS-LC's random-nonce seal (`aead_aes_gcm_seal_scatter_randnonce`, `crypto/fipsmodule/cipher/e_aes.c:1340-1377`, the same on both module lines) keeps no count.

## Decision

**Algorithms (maintainer, 2026-11-03).** `AeadAlgorithm` names AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305, each with a 96-bit nonce and a 128-bit tag, behind one key type, `aead::Key`, which replaces `Aes256GcmKey`. `Algorithm::Aead`, `Family::Aead`, `ProfileSpec::aeads`, `Admitted::aeads()` and `Admitted::admit_aead` follow the other families outside TLS (decision 0008). `assert_admitted_approved` walks the AEAD cells last, after the MAC, KDF and key-agreement cells. *(Amended 2026-11-03, #45: the hash cells now follow the AEAD cells; [decision 0014](0014-hashing.md).)*

**The API (maintainer, 2026-11-03).** `aead::Key::new(&admitted, algorithm, key)` refuses, in order, an algorithm the profile does not admit (`NotInProfile`, or `Unavailable` for one the module line lacks), a key that is not `algorithm.key_len()` bytes (`AeadKeyLength`), and a key the module refuses (`AeadKey`). Its decision logic is in a helper `new` calls, because cargo-mutants does not mutate a method named `new` (#40). `seal_in_place(aad, buf)` returns the nonce and the tag, and `open_in_place(nonce, aad, buf)` takes the nonce stored beside the ciphertext. `Key` is not `Clone`, and its `Debug` names the algorithm only.

**Nonces are chosen inside the crate, never by the caller (AES-GCM by the module's seal, ChaCha20-Poly1305 from the module's DRBG).** SP 800-38D §9.1 (p. 22) puts the IV's generation unit inside the module's boundary, and FIPS 140-3 IG C.H accepts two protocol-independent IV constructions, both inside the module: Scenario 2, random (p. 151), and Scenario 3, deterministic (pp. 151-152). The crate uses Scenario 2.

- **AES-GCM** seals through aws-lc-rs's `RandomizedNonceKey`: AWS-LC draws a 96-bit IV from its DRBG inside the seal (`aead_aes_gcm_seal_scatter_randnonce`), and the module marks that seal approved. A seal under a nonce from outside the module is never marked approved, on either line.
- **ChaCha20-Poly1305** has no random-nonce key in aws-lc-rs (`aws-lc-rs-1.18.2/src/aead/rand_nonce.rs:49` refuses it). The crate draws 12 bytes through its own `random::fill`, the module's DRBG, and seals through `LessSafeKey`; aws-lc-rs does the same for AES-GCM-SIV. Only `unrestricted` admits ChaCha20-Poly1305, which is outside the module's boundary on both lines (`bcm.c` asserts `CRYPTO_chacha_20` is not in the module's text).
- **One construction per key** (SP 800-38D §8.2, p. 19): a key never seals under any other IV source.

**The seal limit (maintainer, 2026-11-03).** Each `Key` holds an atomic count. `seal_in_place` reserves an invocation before it calls the module, with a compare-and-swap that never wraps, and refuses the 2^32 + 1th seal with `CryptoError::AeadLimit`, for all three algorithms. A reserved invocation is spent even if the seal then fails. Opening is not counted: IG C.H Additional Comment 7 (pp. 154-155) places no IV requirement on the decrypting module. The count belongs to the key object (residual 1).

**Plaintext length.** Checked before the count and the module: at most 2^36 − 32 bytes for AES-GCM (SP 800-38D §5.2.1.1, p. 8, len(P) ≤ 2^39 − 256 bits), and 274,877,906,879 bytes for ChaCha20-Poly1305 (one byte below RFC 8439 §2.8's P_MAX of 274,877,906,880, because the module refuses that length). A longer plaintext is `CryptoError::AeadPlaintextLength`. `AeadAlgorithm::max_plaintext_len()` gives the bound.

**The tag** is always 16 bytes: SP 800-38D §5.2.1.2 (p. 9) lets an implementation support a single tag length, RFC 7518 §5.3 requires 128 bits for JOSE, and RFC 8439 §4 forbids truncation. `open_in_place` refuses a buffer shorter than the tag with `CryptoError::AeadOpen`.

**Profiles.** Each profile admits from its own text (decision 0008):

| Profile | Admits, in preference order | Governing text |
|---|---|---|
| `unrestricted` | AES-256-GCM, AES-128-GCM, ChaCha20-Poly1305 | The backends' inventory |
| `preferred` | AES-256-GCM, AES-128-GCM | ISM p. 6 (AES the only approved symmetric algorithm); ISM-1769 (p. 11), "preferably AES-256"; GCM named on p. 11, preferred by ISM-1771 (p. 15) and ISM-0998 (p. 16), and required for TLS by ISM-1369 (p. 20). ChaCha20-Poly1305 refused: p. 6, ISM-0471 (p. 7) |
| `bsi` | AES-256-GCM, AES-128-GCM | TR-02102-1 Table 3.1 (p. 40), Table 3.2 (p. 42), §3.1.2 (pp. 42-43). ChaCha20-Poly1305 refused: §3.2 (p. 44), "no dedicated stream ciphers are recommended" |
| `fips1403` | AES-256-GCM, AES-128-GCM | The CMVP SP 800-140C list §6.2.2.1 (FIPS 197-upd1, SP 800-38D), through SP 800-140C r2 §6.2 (p. 2); SP 800-131A r2 Table 1 (p. 7). ChaCha20-Poly1305 refused: SP 800-140C r2 §6.1 (p. 2) precludes every function not on the §6.2 list |
| `fips1402` | AES-256-GCM, AES-128-GCM | FIPS 140-2 Annex A (pp. 1, 3); FIPS 140-2 IG A.5 |
| `cnsa1` | AES-256-GCM | CNSSP 15 (2016) Annex B ¶1 (p. B-1), "Use 256 bit keys"; RFC 9151 §4 (AES-256 in GCM). `Options::cnsa1_unclassified_nss` does not widen it: ¶2b (p. B-2) names RSA, DH and SHA-256 only |
| `cnsa2` | AES-256-GCM | CNSSP 15 (2024) Annex B ¶1 (p. B-1); ¶8a and footnote 1 (p. 5) keep RFC 9151 and RFC 9206 for protocol guidance |

AES-128 "will not be approved beyond 2030" under the ISM (p. 11); `preferred` keeps AES-128-GCM until a later transition point, as it does HMAC-SHA256. NIST (IR 8547 §4.1.3, Table 6, p. 18) and BSI set no end date for AES.

**Module cells.**

| Cell | 3.x | 4.x dynamic | 4.x static |
|---|---|---|---|
| AES-128-GCM, AES-256-GCM | `Approved` | `AlgorithmTested` on A7840 | `AlgorithmTested` on A7887 |
| ChaCha20-Poly1305 | `NotApproved` | `Unverified` | `Unverified` |

- **3.x AES-GCM outside TLS is `Approved` (maintainer, 2026-11-03).** Table 5 (p. 8 of both security policies) lists AES-GCM with IV generation Internal, mode 8.2.2, keys 128 and 256. §2.7 ("GCM IV", Scenario 2; pp. 18-19 of #5314, p. 19 of #5298) claims compliance with IG C.H Scenario 2 for `EVP_aead_aes_128_gcm_randnonce()` and `EVP_aead_aes_256_gcm_randnonce()`, the functions `RandomizedNonceKey` calls. §2.11 (p. 21) says GCM with internal IV generation "shall only be used in conjunction with the TLS protocol"; it sits under "Industry Protocols" and describes the TLS IV construction (Scenario 1). Unlike ECDH (decision 0011), the policy makes a positive, protocol-independent claim that names the crate's exact functions, and IG C.H Additional Comment 1 (p. 153) calls Scenario 2 protocol independent.
- **4.x AES-GCM is `AlgorithmTested`** on the lowest-numbered certificate of each build that shows both operations the key performs: "AES-GCM, Direction Encrypt, IV Generation Internal, IV Generation Mode 8.2.2" for the seal and "Direction Decrypt, IV Generation External" for the open, each with the key length, a 96-bit IV and a 128-bit tag. A7840 (dynamic, AESNI_AVX512) and A7887 (static, AESNI_AVX512) show the same capability text.
- **The DRBG is not required on the same certificate (maintainer, 2026-11-03).** No AES-GCM certificate shows the Counter DRBG, which the module offers as a separate, module-wide service. The certificate's "IV Generation Internal, 8.2.2" capability is the internal-IV encryption itself, so decision 0004 §2 is met by one certificate; §3's ECDH example, where key generation is an operation the cell's API performs, does not apply.
- **ChaCha20-Poly1305** appears in neither 3.x security policy (`NotApproved`, as the ChaCha20 TLS suites are), and on 4.x, with no policy and no CAVP algorithm for it, stays `Unverified`.
- **No limit from the policies.** Neither 3.x policy states a 2^32 invocation limit for Scenario 2, or any GCM plaintext limit; the crate's limits come from SP 800-38D.

`assert_admitted_approved(&admitted, &[Family::Aead])` passes every profile but `unrestricted` on the 3.x line, and refuses every profile on 4.x.

**The sealed box.** `sealbox` builds its AES-256-GCM key with `aead::Key::new`, and its admission step refuses unless the profile admits ECDH on P-384, HKDF-SHA384 and AES-256-GCM. Every profile that admitted the sealed box already admits AES-256-GCM, so none loses it. The construction and wire format are unchanged: a blob sealed by 0.9.0 opens.

**The test hook.** `test_support::aead_set_invocations` sets a key's count, so the conformance suite reaches the limit without sealing 2^32 times. It is compiled only for the crate's tests and under the `test-support` feature. Enabling `test-support` outside a test build lets a caller reset a key's count, so a production dependency graph must not enable it.

## Named residuals

1. **The count is per key object.** SP 800-38D §8.3 counts every instance that uses the key. The same key bytes loaded into two `Key`s, or into two processes, get a count each. The caller owns key uniqueness.
2. **BSI prefers deterministic IVs.** TR-02102-1 §3.1.2 (p. 42): deterministic IVs "should be preferred" if possible. The crate uses random ones, which the same paragraph accepts with the 2^32 limit the count enforces.
3. **HPKE and MLS seals cannot be built on `aead`.** Their nonces are deterministic and come from the key schedule (RFC 9180 §5.2). A caller-supplied seal nonce is off the approved path on both lines (SP 800-38D §9.1; IG C.H has no scenario for it). Opening is not affected.
4. **CMS's default tag is 12 octets** (RFC 5084 §3.2). The crate writes 16-octet tags, which CMS allows when encoded explicitly, and cannot open a message sealed with a 12-octet tag.
5. **Per-call residue.** Each AES-GCM seal and open copies the GHASH key table into a stack context the module never cleanses, and ChaCha20-Poly1305 leaves its one-time Poly1305 key on the stack, on both lines (`e_aes.c`, `aead_aes_gcm_seal_scatter_impl` and `aead_aes_gcm_open_gather_impl`; `crypto/cipher_extra/e_chacha20poly1305.c:116-141`). The key schedule itself is held in the module's AEAD contexts, which the module cleanses when the key drops.
6. **The approval indicator is invisible.** aws-lc-rs keeps AWS-LC's per-call service indicator crate-private, so the crate cannot read it.
7. **The AES-GCM cells claim the tested ranges only.** On 4.x, A7840 and A7887 tested AES-GCM with payloads of 128-65536 bits in steps of 128 and AAD of 0-320 bits. `aead` seals and opens any plaintext up to 2^36 − 32 bytes, with any AAD; lengths outside those ranges are not CAVP-sampled (decision 0004 §5).

## Consequences

- `Aes256GcmKey` and `aead::KEY_LEN` are removed: `aead::Key::new(&admitted, AeadAlgorithm::Aes256Gcm, key)` and `AeadAlgorithm::key_len()` replace them.
- A caller sealing more than 2^32 times needs a new key, and gets `AeadLimit` rather than a silent breach of SP 800-38D §8.3.
- Decision 0004 §4 is corrected for the 4.x static certificates, which this work found; decisions 0001, 0008, 0010, 0011 and 0012 note what this decision settles.
